SmartCare MLOps architecture

How patient vitals move from wearable devices to a live risk dashboard, how models are trained and deployed, and which tool does what.

Lab project with simulated data. Monitoring and observability are not implemented yet. DevSecOps scanning is a possible future enhancement.

1Data ingestion

  1. The simulator creates 2,000 patients. Each one has its own normal heart rate, oxygen and temperature (Python).
  2. Every patient sends one event per minute: heart rate, SpO₂, temperature, steps, battery.
  3. About 2% of events are made dirty on purpose: a missing value, heart rate 0 or 250, a late timestamp, a duplicate.
  4. Events go to the Kafka topic wearables.vitals, keyed by patient.

The simulator sends one event per device every 60 seconds, about 33 events per second in total.

2Real-time processing

  1. Kafka keeps the events for 3 days. Two readers use the same stream.
  2. Kafka Connect copies the events to MinIO, in one folder per event date.
  3. Flink reads the topic, blanks impossible values, and groups events by patient in 5-minute event-time windows.
  4. For each window Flink computes 5 features and calls BentoML, which answers with a risk score.
  5. Flink writes every window to scores and every score of 0.8 or more to alerts in PostgreSQL.
  6. Streamlit reads PostgreSQL and refreshes the dashboard every 10 seconds.

Kafka Connect saves the raw stream to MinIO. Separately, Flink turns events into five-minute patient features. BentoML serves the XGBoost model, and predictions go to PostgreSQL for the Streamlit dashboard.

3Batch ETL and feature engineering

  1. Airflow starts the etl_vitals DAG for the days you choose.
  2. DuckDB reads that day's raw files from MinIO.
  3. Duplicate events are removed.
  4. Impossible values (heart rate 0 or 250) become empty, so they do not spoil averages.
  5. Events are grouped into 5-minute windows per patient, and the 5 features are computed.
  6. Each window is joined with the crisis list, which gives the label 0 or 1.
  7. The result is saved as Parquet in clean-data/features/date=….

Airflow runs the historical ETL. DuckDB cleans, deduplicates and aggregates the data, then saves the features as Parquet in MinIO.

4Model training and evaluation

  1. Read all feature days from MinIO and sort them by time.
  2. Split by time: the oldest 80% train the model, the newest 20% test it.
  3. Train XGBoost. scale_pos_weight makes the rare crises count more.
  4. Measure F1, recall, precision and PR-AUC on the test part.
  5. If F1 reaches the minimum, MLflow registers a new model version with the alias candidate. If not, the job fails.

The workflow trains and evaluates XGBoost, tracks metrics in MLflow, and registers a candidate model only if it meets the F1 threshold, which you set when you start the workflow (default 0.5).

5CI/CD and k3s deployment

  1. train: train and register the model in MLflow. The job gives the version number to the next jobs.
  2. eval: compare candidate with production on the same test data. A worse model stops the pipeline.
  3. build: download the model, build the Docker image with the model inside, and test it.
  4. push: send the image to Docker Hub, tagged with the model version.
  5. deploy: apply the manifest to k3s. Pods are replaced one by one (rolling update).
  6. smoke: call the live API. It must answer with the new model version and sensible scores. A failure rolls back.
  7. promote: the MLflow alias production moves to this version.

One manually triggered GitHub Actions workflow runs seven jobs on a self-hosted runner: train, eval, build, push, deploy, smoke and promote. The build job also tests the image before it is pushed. If the rollout or the smoke test fails, the deployment is rolled back and the model is not promoted.

6Tools and why we use them

Each card says what the tool is, why it is in this project, and where it runs.

Ingestion and streaming

Python simulator

What A script that makes fake wearable events and the list of crises.

Why No real patient data is needed, and we control volume, dirty data and the true labels.

vm-sim
Apache Kafka

What A log that holds the event stream.

Why One entry point for all data. Flink and MinIO read the same stream, and events are kept 3 days, so a slow reader loses nothing.

vm-kafka
Kafdrop

What A web page to look inside Kafka.

Why See topics, messages and consumer lag while debugging.

vm-kafka
Kafka Connect (S3 sink)

What Copies Kafka topics to MinIO with no code.

Why Keeps a raw copy for training, in folders by event date.

vm-kafka
Apache Flink

What A stream processor that remembers state.

Why Five-minute windows per patient need memory and event time. BentoML cannot do this.

vm-flink

Storage and batch

MinIO

What Object storage with the S3 API, run by us.

Why One place for raw events, training data and MLflow files.

vm-data
Apache Airflow

What A scheduler for pipelines.

Why Runs the ETL day by day, retries failures and keeps a history. It does the ETL only, not the training.

vm-mlops
DuckDB

What A SQL engine inside the Python process.

Why Reads JSON and Parquet in MinIO directly and is fast on one small machine, so Spark is not needed.

Why Small, typed and fast. Training reads only the columns it needs.
